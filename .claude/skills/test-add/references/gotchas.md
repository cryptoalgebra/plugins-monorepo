# Gotchas and advanced testing patterns

Referenced from `test-add`'s SKILL.md. Read this before writing a new fixture from scratch, and whenever a test fails in a way that doesn't look like your own logic is wrong — most of these entries were mistaken for a real bug at first.

**This file is a running log.** If you hit something during test-add work that cost real debugging time and could plausibly happen to someone else again — a non-obvious library behavior, a missing config entry, an environment quirk, anything you had to dig for the real cause of — add it as a new bullet before finishing the task, in the same shape as the existing entries: what the symptom looks like, why it happens, and the fix. Only add things you've actually verified by hitting them yourself; don't add speculative "this might also happen" guesses.

## Testing private/internal math directly

If the behavior you need to test is a `private` (or `internal`) pure function buried inside a stateful contract — not reachable through a clean public entry point without a lot of unrelated setup — don't force it through the full public flow and don't copy its logic into a new test file (a copy validates the copy, not the real function, and drifts silently if the original changes). Instead: change its visibility to `internal` (a no-op behavior change) and add a thin wrapper contract under `contracts/test/` that inherits the real contract and exposes a public passthrough. See `packages/price-convergence/contracts/test/PriceConvergenceVaultQuoteHelper.sol` (wraps `PriceConvergenceVault._quoteAtSqrtPrice`) and `packages/price-convergence/contracts/test/VaultMathTestHelper.sol` (wraps library calls) for the pattern — as of writing that package only exists on the `pc-vault-tests` branch, not yet on `master`; if it isn't in your checkout, treat this as a general technique rather than a literal file to open.

## Testing cross-layer rounding/composition gaps

When a pure math/library helper computes a budget for a *sequence* of real operations (e.g. splitting one combined balance into liquidity for two positions, each minted separately against a live pool), a helper that's internally correct in isolation can still be wrong once composed with the real call site, because the real call may round differently than the helper did. Don't assume this reverts or succeeds — reproduce it: repeatedly re-query the calculator with its own previously-returned "used" totals as the next input until the totals stop shrinking (reducing the budget can shift which side binds, so it's rarely a single round-trip), fund the real contract with exactly that converged, slack-free amount, then run the actual on-chain sequence and assert on what actually happens. See `packages/price-convergence/test/PriceConvergenceVault.spec.ts` ("mints both positions cleanly even when funded to VaultMath's own tightest computed budget") for a worked example (`pc-vault-tests` branch, not yet on `master`) — there the real pool turned out to self-correct (clamping the granted liquidity down) rather than reverting, which the test now pins down as a regression check.

## Known gotchas when writing new fixtures

These cost real debugging time in practice — check them before assuming a failure is a real bug:

- **`createPool()` / `computeAddress()`** (in `test-utils/externalFixtures`) assume the two tokens are already sorted by address, the way `tokensFixture()` returns them. Pass your own tokens in whatever order you happened to deploy them and the pool can attach to an address nothing was ever deployed at — the symptom is `Transaction reverted: function returned an unexpected amount of data` on some later call, not on `createPool()` itself, so it's easy to misdiagnose. Sort by address before calling: `BigInt(await tokenA.getAddress()) < BigInt(await tokenB.getAddress()) ? [tokenA, tokenB] : [tokenB, tokenA]`.
- **`evm_snapshot` / `evm_revert`**: the returned snapshot id is single-use — `evm_revert` consumes it. If you're reverting to the same point across a loop of scenarios, reassign the id from `evm_snapshot`'s return value on every iteration; reusing a stale id doesn't error, it just silently does nothing, and state quietly leaks between "isolated" cases.
- **Missing `dependencyCompiler` entries**: the first time a package's tests need beacon-proxy infrastructure (`BeaconProxyDeployer.sol` and similar) that no existing spec file in that package has needed yet, `ethers.getContractFactory('BeaconProxyDeployer')` fails with `HH700: Artifact for contract "BeaconProxyDeployer" not found`. Compare the package's `hardhat.config.ts` `dependencyCompiler.paths` against a sibling package that already has beacon-proxy tests (e.g. `access-list`) and add whatever's missing.
- **Plugin mocks that don't implement the full `IAlgebraPlugin` hook surface** (a mock built for one specific interface, not the whole plugin ABI): triggering a real swap through a pool with that mock still wired as the plugin fails with `function selector was not recognized and there's no fallback function`, because the pool tries to call `beforeSwap`/`afterSwap` on it. Call `pool.setPluginConfig(0)` to disable hooks before the swap, matching the existing `packages/*/test/*.spec.ts` tests that already do real swaps.
- **`transferFrom`-based balance-shortfall fallbacks** (a pattern like `if (balance < amount) token.transferFrom(externalFunder, ...)`, seen inside `_paySwap`-style helpers): the ERC20 `approve` has to target the contract that actually calls `transferFrom` — usually the vault/plugin itself — not whatever it forwards the tokens to (the pool). Approving the wrong address fails with `ERC20: insufficient allowance` and can look like a balance problem at first glance.
- **`packages/default-plugin/test/integration/Integration.spec.ts`** is a mainnet(-fork) integration test — it calls `ethers.getContractAt` against real, hardcoded Base-network addresses and `impersonateAccount`s the real factory owner, unlike every other spec file's plain mock-deploy fixture. As of writing it currently fails outright (`could not decode result data`) because the fork config it needs (`hardhat.base.config.ts`'s `networks.hardhat.forking`) is commented out repo-wide. If you're not specifically working on that file, its failures aren't a regression you caused — don't spend time debugging it.
