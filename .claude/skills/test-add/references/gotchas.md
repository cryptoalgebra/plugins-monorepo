# Gotchas

Referenced from `test-add`'s SKILL.md. Read this before writing a new fixture from scratch, and whenever a test fails in a way that doesn't look like your own logic is wrong — most of these entries were mistaken for a real bug at first.

**This file is a running log.** If you hit something during test-add work that cost real debugging time and could plausibly happen again — a non-obvious library behavior, a missing config entry, an environment quirk, anything you had to dig for the real cause of — add it as a new bullet before finishing the task, in the same shape as the existing entries: what the symptom looks like, why it happens, and the fix.

Two rules for adding entries:

- **Only what you hit yourself and verified.** No speculative "this might also happen" guesses.
- **Only what generalizes to this repo.** A trap in shared infrastructure (`test-utils`, hardhat config, the pool/plugin interaction) belongs here. A one-off quirk of a single contract belongs in a comment in that contract's own spec file.

Don't put dates, file counts, or "last touched" claims in this file — they rot silently and no one re-checks them. Describe behavior, not census data.

## Known gotchas when writing new fixtures

- **`createPool()` / `computeAddress()`** (in `test-utils/externalFixtures`) assume the two tokens are already sorted by address, the way `tokensFixture()` returns them. Pass your own tokens in whatever order you happened to deploy them and the pool can attach to an address nothing was ever deployed at — the symptom is `Transaction reverted: function returned an unexpected amount of data` on some later call, not on `createPool()` itself, so it's easy to misdiagnose. Sort by address before calling: `BigInt(await tokenA.getAddress()) < BigInt(await tokenB.getAddress()) ? [tokenA, tokenB] : [tokenB, tokenA]`.
- **`evm_snapshot` / `evm_revert`**: the returned snapshot id is single-use — `evm_revert` consumes it. If you're reverting to the same point across a loop of scenarios, reassign the id from `evm_snapshot`'s return value on every iteration; reusing a stale id doesn't error, it just silently does nothing, and state quietly leaks between "isolated" cases.
- **Missing `dependencyCompiler` entries**: the first time a package's tests need infrastructure (`BeaconProxyDeployer.sol` and similar) that no existing spec file in that package has needed yet, `ethers.getContractFactory('BeaconProxyDeployer')` fails with `HH700: Artifact for contract "BeaconProxyDeployer" not found`. Compare the package's `hardhat.config.ts` `dependencyCompiler.paths` against a sibling package that already has such tests and add whatever's missing.
- **Plugin mocks that don't implement the full `IAlgebraPlugin` hook surface** (a mock built for one specific interface, not the whole plugin ABI): triggering a real swap through a pool with that mock still wired as the plugin fails with `function selector was not recognized and there's no fallback function`, because the pool tries to call `beforeSwap`/`afterSwap` on it. Call `pool.setPluginConfig(0)` to disable hooks before the swap, matching the existing tests that already do real swaps. **Set it back afterwards** if anything later in the test calls a contract that checks the pool's plugin flags — a vault or plugin that requires an oracle will otherwise reject the next call with its own "oracle not connected" error, which looks nothing like the swap setup that actually caused it.
- **`transferFrom`-based balance-shortfall fallbacks** (a pattern like `if (balance < amount) token.transferFrom(externalFunder, ...)`): the ERC20 `approve` has to target the contract that actually calls `transferFrom` — usually the plugin itself — not whatever it forwards the tokens to (the pool). Approving the wrong address fails with `ERC20: insufficient allowance` and can look like a balance problem at first glance.
- **`packages/default-plugin/test/integration/Integration.spec.ts`** is a mainnet-fork integration test, unlike every other spec file's plain mock-deploy fixture: it calls `ethers.getContractAt` against hardcoded Base addresses and `impersonateAccount`s the real factory owner. The hardhat network no longer boots on a fork, so this suite establishes one itself in its `before` hook from `BASE_FORK` exported by the root `hardhat.base.config.ts`, which reads `ANKR_API_KEY` from the root `.env` and pins a block number. Nothing guards a missing key: without it, or without network, the `before` hook dies and takes the whole `default-plugin` run with it. If it fails while every mock-based test passes, check the key and fork reachability before treating it as a regression you caused.

- **On a range one tick wide, "used nothing" is not the same state as "no position".** A single wei of leftover token spread over one tick is worth tens of thousands of liquidity units (a tick is ~0.005% wide, so liquidity per wei is ~1/0.00005), while `getAmountsForLiquidity` on that liquidity rounds back down to zero or one wei. So a position can report `used0 == used1 == 0` and still have been minted with real liquidity, and a test asserting "nothing was left over" must assert on `liquidity`, not on the `used` amounts. The reverse also bites: driving a leftover to exactly zero by feeding a position's own `used` total back in as the next budget does not converge — `getAmountsForLiquidity(getLiquidityForAmounts(x))` tends to land on `x - 1` in that neighbourhood rather than on a fixed point, so a "no leftover at all" state can be unreachable at normal prices even though it looks one iteration away. Zero liquidity for a nonzero leftover only happens at deeply negative ticks, where a wei of token0 buys less than one unit of liquidity.

- **`reset()` with no arguments drops the fork.** hardhat-network-helpers sends `hardhat_reset` with empty params, which resets to a clean **non-forked** chain rather than re-forking from the configured URL. Any spec file that calls it in a `before` hook — `AlgebraPool.gas.spec.ts` does — silently kills the fork for every spec mocha runs afterwards, and since mocha orders files by path, `integration/` sorts last and is always the victim. The symptom is `could not decode result data (value="0x")` from a contract that plainly exists on the fork, and running that spec file on its own passes, which makes it look like the endpoint is flaky. This is already handled: the fork suite re-establishes the fork in its own `before` hook via `reset(BASE_FORK.url, BASE_FORK.blockNumber)`, so it does not depend on file order. Keep that shape if you add another fork suite, and note the constant is now exported as `BASE_FORK` rather than read out of `networks.hardhat.forking`, which the root config no longer sets. Running one spec in isolation is not enough to clear a fork test — run the whole package.

- **`OnlyPool()` under `hardhat coverage` means a proxy was compiled fresh instead of from pinned bytecode.** `solidity-coverage` sets `settings.optimizer.enabled = false` for every compilation job (unless `viaIR` is on), and `UpgradeableAbstractPlugin._getPool()` reads the pool address out of the proxy's runtime bytecode at a hardcoded `POOL_ADDRESS_OFFSET = 75`, which is only where the `pool` immutable lands under the package's normal optimizer settings. With the optimizer off the proxy grows from 457 to 542 bytes, the address moves to offset 130, and every hook reverts.

  This is solved, so do not work around it and do not dismiss a coverage row as noise: every package with tests now runs clean under coverage, `limit-order` and `default-plugin` included. The fix is to deploy the proxy from bytecode pinned at production settings — `packages/test-utils/pinnedProxy.ts` for a proxy the spec creates, and a pinned harness *factory* (`packages/default-plugin/test/shared/pinnedFactory.ts`, `packages/limit-order/test/pinned/`) where the proxy is built by `new AlgebraPluginProxy` inside a contract's own compilation unit. If you hit `OnlyPool()` in a new fixture, you are deploying a proxy from a fresh artifact; route it through the pinned factory instead. `skipFiles` cannot help — the proxy lives in `node_modules` — and neither can a per-file `solidity.overrides` entry, because the plugin rewrites the compilation job for overridden files too. Regenerate pinned blobs with `packages/test-utils/scripts/regeneratePinned.js`; the `PinnedProxyBytecode` and `PinnedFactoryBytecode` specs fail if they drift.

- **A `MockTime*` plugin behind a beacon proxy starts its clock at zero, not at `TEST_POOL_START_TIME`.** `MockTimeAlgebraUpgradeablePlugin` declares `uint256 public time = 1601906400;`, but a state-variable initializer runs in the constructor, which for a beacon proxy executes against the *implementation's* storage. Read `time()` through the proxy and it is `0`. This matters wherever the oracle subtracts a period from the current time — `canGetTwap(period, currentTime)` computes `currentTime - period` on a `uint32`, so with a small mock clock and a realistic TWAP period it underflows into overflow-comparison territory rather than simply returning false. Advance the clock to a comfortable base (`advanceTime(100000)`) **before** initializing the pool, so the oldest timepoint carries a large timestamp and the arithmetic stays in range.

- **`initializer` runs before the plugin's own `onlyPluginFactory`.** On `AlgebraUpgradeablePlugin.initialize` the modifiers are ordered `initializer onlyPluginFactory`, so calling it again on a live plugin always reverts with `Initializable: contract is already initialized`, whoever the caller is — the factory guard is unreachable there. To assert `OnlyPluginFactory` you need a proxy that was never initialized: deploy `AlgebraPluginProxy(beacon, pool, '0x')` directly and attach the plugin ABI to it. The same proxy is what you need to assert the `PluginInitialized` event, since going through the factory means the plugin address is not known until after the transaction and `.to.emit(contract, ...)` needs it upfront.

- **Never combine snapshot updating with a filtered run.** `UPDATE_SNAPSHOT=1` (or `--update`) deletes every snapshot the run did not touch, so pairing it with `--grep`, `.only`, or a single spec file silently wipes the baselines of everything filtered out. Update snapshots only from a run that executes the whole suite the `.snap` file belongs to. The inverse is harmless and expected: a filtered run reports the untouched entries as "obsolete", which is noise, not a problem.

- **Renaming a `describe` orphans its snapshots.** Snapshot keys are the full title chain, so adding a tag like `[ @slow ]` to a suite makes every entry underneath it a new key and leaves the old ones behind as dead weight. If the suite cannot be updated in a full run (see above), delete the stale keys from the `.snap` file by hand, and check the diff reads as renames rather than additions.

- **Touching a contract a gas suite measures through moves the recorded gas, and what you touch need not be on the measured path at all.** Two shapes of this have bitten here. `packages/default-plugin/test/AlgebraPool.gas.spec.ts` snapshots swaps with `MockTimeVirtualPool` wired in as the farming incentive, so an extra `SSTORE` inside that mock's `crossTo` shows up as a gas regression in half a dozen unrelated snapshots. The cheaper one to miss: adding an external function to a `contracts/test/` harness enlarges its selector dispatch, and `AdaptiveFeeTest.getGasCostOfGetFee` reads `gasleft()` from inside that same contract, so two added selectors moved all three of its snapshots by four gas (548 to 552, 1272 to 1276) without `AdaptiveFee` itself changing by a line. In both cases the numbers measure something else entirely, so updating them records noise as a baseline. Add a second contract instead of widening the one the gas suite uses: `AdaptiveFeePropertiesTest.sol` exists for exactly that. Note that neither shape shows up under `hardhat coverage`, since gas suites are tagged `@skip-on-coverage`, so only a full `npx hardhat test` of the package reveals it.

- **The two ALM rebalance corpora are driven with different pool wiring, and copying the wrong loop's setup fails silently.** In `packages/alm/test/AlmPlugin.spec.ts`, `#rebalance1` replays `almRebalances.json` with `deployedFor(..., 60, true, false)` and `setDecimals(18, 18)`, while `#rebalance3` replays `almRebalances3.json` with `deployedFor(..., 200, false, true)` and `setDecimals(6, 18)` — different tick spacing, the opposite side as deposit token, different decimals. The two loops otherwise look identical, so the setup is easy to copy from the wrong one. Nothing errors when you do: the manager simply computes a different range, and a test that pins the output pins wrong numbers while looking authoritative. Take the setup from the loop that owns the record's file, and if you are pinning an output, get the value from a run rather than from the recording.

- **`loadFixture` does not guarantee stable contract addresses.** Reverting to an earlier snapshot invalidates every snapshot taken after it, so hardhat-network-helpers re-executes those fixtures — and the redeploy lands on a different nonce, which means the same fixture hands out different addresses from one run to the next. Nothing warns you. This bites any test whose outcome depends on a deployed address rather than on a value it set itself, and in this repo that is a wide class, because Algebra sorts a pool's two tokens by address and both the core contracts and several plugin modules branch on that order. The symptom is an assertion about a direction, an ordering, or a specific address that is correct in one run and inverted in the next. Read the addresses inside the test and derive the expectation from them (`BigInt(await tokenA.getAddress()) < BigInt(await tokenB.getAddress())`) rather than hardcoding the side you observed once; where a fixture needs a particular order, do what `packages/limit-order/test/limitOrderFixture.ts` does and redeploy until it holds instead of assuming it.

- **A green `npx hardhat test` does not mean a new test is stable — check it under a full `npx hardhat coverage` too.** This applies to every package here: all thirteen with tests ship a `.solcover.js`, and all of them filter with `grep: '@skip-on-coverage'` and `invert: true` (`volatility-oracle` adds `@slow`). So the coverage run is not the same run — a different set of specs executes, in a different order, before yours. That is enough to shift fixture nonces and the addresses that follow from them (see above), and to change any other state a test reads but does not set itself. The symptom is distinctive and easy to misread: the test passes under `hardhat test`, passes again when you run its own spec file alone under coverage, and fails only in the full coverage run, which makes it look like an instrumentation problem when it is really an ordering dependency. Neither command subsumes the other, so run both before calling a new test done — and if a test only holds under one of them, the test is wrong, not the runner.

- **A random generator that ignores the guards on the path produces a green suite that tests almost nothing.** Any contract that gates on thresholds rejects the overwhelming majority of uniformly drawn inputs at the first check, and a draw that dies there never reaches the logic the property is about. The suite still passes, because a property holds vacuously on inputs that revert or return early. Measured in `packages/alm`: 1200 draws with the three prices sampled independently across a wide band reached a rebalance 4 times, because `_decideRebalance` returns before the state machine once any two prices differ by more than the volatility thresholds. The same 1200 draws with the prices held inside those thresholds reached it 1105 times, and the distinct state transitions observed went from 7 to 17. The same thing bit `packages/sliding-fee` in a different shape: drawing two independent ticks over the whole range makes the squared price ratio dwarf the fee factor every time, so both swaps clamp and the branch that moves the two factors together never runs. With that branch broken on purpose the suite missed it entirely on some seeds even at 400 runs, and drawing the tick delta instead catches it within three draws on every seed tried. Read the guards on the path first, then write the generator to straddle each threshold on purpose rather than uniformly. Two habits find this: plant a fault inside the branch you believe you are reaching and check that it dies, and where a suite depends on the tuning, assert it — `AlmPlugin.fuzz.spec.ts` counts the draws that reached the range builder and fails if a change to the generators stops feeding it, which no coverage number would catch.

- **A property test encodes a model, and a wrong model reports a contract bug that is not there.** Checking `VolatilityOracle._volatilityOnRange` against the bound "cannot exceed the largest squared deviation" produced 1382 violations in 1500 draws, which reads exactly like an overflow in unchecked arithmetic. The function returns the *sum* of the squared deviations over `dt` seconds rather than their mean, so the real bound carries a factor of `dt`, and the same draws pass against it. Derive the property from the arithmetic itself, or from the comment above it, before trusting a failure. A property test fails loudly and points at the contract, so an unchecked assumption costs an investigation rather than leaving a silent gap.

- **A property that writes state stops testing anything once a run trips a latch.** `fc.assert` hands the next run whatever the previous one left on chain, so any sticky state carries over. In `packages/alm` the extreme volatility arm calls `_pause()`, and a paused plugin turns every later `rebalance` into a no-op: the run finished with 1 of its 200 draws reaching a rebalance at all, and the property still passed, because a property that asserts on emitted events holds vacuously when nothing is emitted. Nothing in the coverage number would have shown it either, since the corpus covers those lines anyway. Two habits catch it together: reload the fixture inside the property body whenever the property writes state, and assert a floor on how often the interesting path was actually reached. The reload stops the leak, the floor tells you when a change to the generators stopped feeding the path.

- **A property can be live and still miss the fault at the run count you committed.** `AdaptiveFee.sigmoid` is documented never to exceed its alpha, and a property asserting that does catch a planted off by one in it, but only after 20000 uniformly drawn inputs: the bound is slack almost everywhere and binds only where `x` sits a few gammas above `beta`. Drawing `x` as `beta + k * gamma` with `k` spread across the active band catches the same planted fault in 17 to 115 draws depending on the seed, in under a second. When a property asserts a bound, work out where that bound is tight and generate into that region deliberately. Then measure the margin rather than assuming it: six seeds spread from 17 to 115 draws, close enough to a 150 run default to be luck, so that property runs four times the shared count. Proving a property can fail at some run count is not the same as proving it fails at the one you shipped, so plant a fault, sweep a few seeds, and set the default above the worst of them.

- **A coverage run over a build directory that plain test runs have touched can report 0% for contracts whose tests plainly passed.** After several rounds of alternating `npx hardhat test` and `npx hardhat coverage` in `packages/alm`, a coverage run finished with all 2192 tests passing and still showed `RebalanceManager.sol`, `AlmConnector.sol` and `AlmPluginImplementation.sol` at zero across the board, with `BaseRebalanceManager.sol` down from 93% branches to 60%. The run was also visibly quicker than usual, 107 seconds against 154, which is the tell: it did not instrument everything it reported on. Deleting `artifacts`, `cache`, `coverage` and `coverage.json` and running again reproduced the real numbers exactly. So do not read a sudden collapse to zero as a lost test, and do not chase it in the specs. Clear the build directory first, and prefer a clean directory whenever a coverage number is going to be quoted.

## Testing private or internal functions directly

If the behavior you need to test is a `private` or `internal` function buried inside a stateful contract — not reachable through a clean public entry point without a lot of unrelated setup — don't force it through the full public flow, and don't copy its logic into a test file. A copy validates the copy, not the real function, and drifts silently when the original changes.

Instead: widen the visibility to `internal` (a no-op behavior change) and add a thin harness contract under `contracts/test/` that exposes a public passthrough. This repo already does this — see `packages/dynamic-fee/contracts/test/AdaptiveFeeTest.sol`, which wraps `AdaptiveFee` library calls behind plain external functions, and `packages/volatility-oracle/contracts/test/VolatilityOracleTest.sol`. Register the harness the same way its siblings are registered, and remember `contracts/test/*.sol` is excluded from coverage targets.
